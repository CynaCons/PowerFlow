2. The flow you practice

Stripped of project specifics, every repo runs the same loop. The PRD sets intent and methodology constraints; decisions are recorded before the subsystem exists; each feature gets an SRS table with stable IDs; PLAN.md carries versioned iterations operated by a single writer; each iteration walks the four movements (RadEAU PRD §9.1) and ends on a smoke test; owner reports and new ideas re-enter as tasks, never as prose. Agents split into a coordinator that owns the documents and workers that own code and memories.

3. The principles, with their sources

These are the rules that recur across repos, stated once. Each card names where I found it so you can check my reading. They become the body of the handbook (§5).

Plan before code; PRD first

Start from the idea, iterate the PRD with the agent until it can guide the rest. The PRD ends with a methodology section and a table of decisions to record.

RadEAU PRD §9, §11 · training deck F1 · PowerGit PRD §9 "Documents"

PLAN.md is the operational backbone

Versioned majors and iterations, a **Goal:** line, checkbox tasks only, Backlog pinned last, exactly one active iteration, append-only, never cleared. Every iteration's last task is a smoke test.

powerplan PRD §4 · RadEAU PLAN.md · PowerNote PLAN.md · powertimelines "Format Rules"

Single writer, evidence or it didn't happen

powerplan is the only sanctioned writer of PLAN.md; a task is ticked with proof (test output, commit, artifact) — a process rule, not a tool parameter. Build passing ≠ feature working.

powerplan PRD §3 · PowerGit AGENTS "Engineering rules" · powertimelines CLAUDE.md §6

A header that cannot go stale

"The current iteration is the last heading not marked COMPLETE." No version number in the header, no Recent-Achievements list to maintain.

PowerGit PLAN.md "Current Status" — versus powertimelines' 110-line achievements list that drifted

One SRS per feature area, ASPICE-style

A table opens the file: ID · Requirement (one shall) · Rationale · Verification (Test/Analysis/Review/Demo) · Trace. IDs are stable forever and never reused; a single index allocates prefixes; CI fails on duplicates. A named feature does not ship without an SRS file.

PowerGit docs/srs/README.md · powerplanner spec/srs/README.md · RadEAU REQUIREMENT_IDS.md + check-req-ids.mjs

Spec updates land with the code

PLAN.md and the relevant SRS are updated in the same change as the implementation. New feature → SRS rows + IDs + a PLAN task before implementation begins.

RadEAU PRD §9.2, §9.5 · powerplanner AGENTS "Native SRS + E2E discipline" · PowerNote CLAUDE "Critical Workflow"

Decisions are written before the subsystem

One ADR per decision (Context / Decision / Consequences), enumerated in the PRD with a default recommendation, each carrying the gate that would reopen it.

RadEAU docs/decisions/D1–D9 · PRD §11

AGENTS.md is the source; CLAUDE.md is a shim

One shared briefing for every harness (Codex, Copilot, Claude, Cursor). CLAUDE.md points at it. Project shape, commands, how we verify, who owns which files, engineering rules, reporting format.

PowerGit · powerplanner · ARXMLExplorer · training-101 (all converged on the shim)

Coordinator / worker split with an ownership table

Coordinator owns PLAN, PRD, SRS, AGENTS and commits. Workers own product code scoped to the task, may write memories, must not commit or edit planning files. Dispatch prompts carry goal, context, constraints, definition of done, report-back format.

PowerGit AGENTS "Who owns which files" · powertimelines CLAUDE.md Part 2 · onslide-coordinator "dispatch contract"

Recursive improvement via memories

docs/agents/memories/<topic>.md: one fact per heading, dated if it might rot, corrected in place. context/<feature>.md is a worker briefing deleted once absorbed. No task status, no secrets, no SRS copies.

PowerGit docs/agents/README.md (55 memories) · powerplanner AGENTS "Memory Files"

Close the loop — by architecture

The agent must be able to see its own work: real binary over CDP, data-testid on every interactive element, no mocks, numbered E2E scripts, raw sleeps banned, stable test hooks treated as public API. Observability is a requirement, not an afterthought.

training deck F5 · RadEAU PRD §9.3 · A2L-Forge "NO MOCKS" · PowerGit "How we verify"

Verify once; screenshots are opt-in

Run e2e once; if red, read the first error, fix, run once. Chrome MCP screenshots re-enter the context and dominated a session's token budget. Pixel diffs only when the owner asks.

PowerGit docs/agents/memories/verify-loop.md · AGENTS "How we verify (token budget)"

Owner reports are symptom-first and owner-closed

The first commit is a failing test quoting the owner's sentence verbatim, on the reported platform, asserting what the owner sees. An agent never ticks an owner-report task — it writes "fixed <sha>, awaiting owner verification" and leaves the box open.

PowerGit AGENTS "Engineering rules" (v0.12.1→v0.13.13 lesson) · training deck F5 "Bugs → failing tests first"

Release is a ritual, not a push

Close the iteration first (PLAN is the changelog source). One version source, everything derives; lockstep check script; canonical build only; tag → CI builds artifacts; smoke the packaged artifact; storefront check; then tick the release in PLAN.

PowerGit .claude/skills/release · RadEAU PRD §9.4 · powerplan docs/RELEASING.md

Determinism over instructions

"Everything that can be done deterministically should be." Programs hold the PMT (process, methods, tools): powerplan writes the plan, powerspawn logs IAC.md, CI scripts guard IDs, plan structure and version derivation. Agents reason; they do not bookkeep.

powerspawn DESIGN.md §2.1 · PowerGit ci.yml "static guards (version, plan)"

Commits name the movement

feat(scope), fix, perf, docs(spec), plan: close vX.Y.Z, release: vX.Y.Z. Plan mutations get their own commits; the version rides in the scope.

5. Proposal: PowerFlow

PowerFlow is three things in one repo, and it follows its own method (PRD.md + PLAN.md operated by powerplan, from the first commit — as powerplan and RadEAU did).

  1. METHODOLOGY.md — the handbook. The canonical prose of §3, roughly four pages, written once. Every project's AGENTS.md links to it instead of restating it. This is what a new collaborator or a fresh agent reads.
  2. templates/ — one file per artifact, with the drift points from §4 already decided. powerflow-init stamps them into a new repo and fills the placeholders from a short interview.
  3. skills/ — the flow as executable skills, each one covering a movement of the loop. Installed once at user level as a Claude Code plugin, so every project gets them without copying; the handbook and templates stay harness-agnostic for Codex/Copilot.

Why a plugin and not per-project copies. You already run six plugins from ~/.claude/settings.json. A personal PowerFlow plugin puts the thirteen skills in every session on this machine with one install, and powerflow-audit can later tell a project which version of the pack it was stamped with. Templates still get copied, because AGENTS.md and the SRS index must live in the project for Codex and Copilot to see them.

Why the handbook is a separate file and not the AGENTS.md template. AGENTS.md is loaded every turn and must stay short and project-specific (PowerGit's is already 12 KB). The handbook is the long, stable explanation agents read once — via a link — and humans read to onboard. Splitting them is the same move that turned CLAUDE.md into a shim.

What moves in from other repos. The powerplan ASCII-gantt skill and visual-plan skill currently live in powerplanner but are already written as portable ("copy into any repo with a plan file"). They become powerflow-status. PowerGit's release skill and RadEAU's check-req-ids.mjs become the generic powerflow-release and the guards template. The onslide-coordinator's dispatch contract and integrity checks become the core of powerflow-coordinate, minus the SQL store.

D6 · Distribution

Personal Claude Code plugin (one install, every project) vs copying .claude/skills/ per repo vs both.
